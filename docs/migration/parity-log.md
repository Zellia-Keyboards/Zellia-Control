# Visual parity log

The React app must look, read and animate exactly like the intended Svelte UI
(baseline commit `4f232a2`). Every visible difference between the two is either
fixed or recorded here, with before/after screenshots from the parity harness
(see [Visual parity](../development.md#visual-parity)).

## How to record a deviation

1. Run `npm run parity` (or `npm run parity -- --grep <scenario>`) and open
   `e2e/.artifacts/parity/index.html`.
2. For a difference that is intended, copy its captures into
   `docs/migration/parity/` as `<id>-before.png` (from `captures/baseline/`) and
   `<id>-after.png` (from `captures/react/`), where `<id>` is the log id in
   lower case, e.g. `pl-007-before.png`.
3. Add or update a row below: the capture id(s) it covers, what differs and why
   (spec decision or bug), and the screenshots. Anything not listed here is a
   bug in the React app.

Status values: **planned** (decided, screen not ported yet), **logged**
(ported, screenshots attached), **reverted** (parity restored).

## Behavior changes without a visible difference

These changes from the Svelte behavior show in no capture, and like PL-028 to
PL-046 each needs the product owner's sign-off.

### Shell

- **A page chunk that fails to load** (D18): the page slot shows the error page
  (`500` / `Internal Error`), with the sidebar. SvelteKit first asked its
  `version.json` whether a newer build was deployed and reloaded the page if so;
  the React build has no version file, and the service worker's precache keeps
  the running build's chunks until an update is applied, so only without an
  installed service worker can a redeploy make a chunk fail to load.
- **History when the session ends** (D3): when the keyboard is unplugged or a
  load fails, the shell goes to `/`, replacing the history entry when already on
  `/` (which also cancels a redirect to Remap still loading its page); the
  Update page and a running firmware update stay (PL-004 is the visible part).
  Disconnect goes to `/` and adds one history entry, as the Svelte sidebar's
  `goto('/')` did.

### Remap and profiles

- **Profile card menu from the keyboard** (§7.4 accessibility): Enter or Space
  on a card's menu button opens its menu (the Svelte card handler cancelled the
  button and activated the card instead, so the keyboard could not open it).
  Opened from the keyboard, the menu focuses its first item (keyboard only: the
  item shows the browser's focus ring); the arrow keys, Home and End move
  between the items, which Tab no longer reaches; Escape closes the menu, and
  Tab closes it and moves on from the menu button. When an item closes the
  menu, focus returns to the menu button (also when the item's dialog closes);
  after Hold to Delete it moves to the card that takes the deleted card's place,
  or to Add Profile. Opened with the mouse, the menu leaves the focus where it
  was, as before. Hold to Delete also works with Enter or Space held for 1.5 s.
- **Semantics** (§7.4 accessibility): `type="button"`, `aria-pressed` on the
  Remap category tabs and the profile cards, cards named by their profile name,
  `role="menuitem"` in the profile menu, `aria-haspopup`/`aria-expanded` on the
  menu and dropdown buttons, a labelled category navigation, decorative SVGs
  hidden.
- **Import file input** (bug): reset after every outcome. Svelte kept the file
  after "No available profile slots", so the same file could not be chosen
  again.
- **Profile names in the confirmation messages** (no HTML from user data): are
  text; the Svelte page interpolated them into `{@html}`.
- **Stored profiles** (validation at the boundary): `keyboard-profiles` is
  validated when read: entries that are not profiles are dropped (slots 1–4 are
  recreated, as before), every profile's `id` is its slot, an invalid active id
  falls back to 1. Valid Svelte data reads back unchanged.
- **Imported files** (validation at the boundary): keep the schema's fields
  only (`name` and the four configuration fields); the Svelte store also kept
  any unknown fields.
- **The already active profile chosen in the dropdown** (D7): does not switch
  the keyboard again (a switch reloads the profile from flash).

### Performance

- **Opening the page writes nothing** (D12: selecting must not corrupt
  settings; §1.4). The key selection outlives navigation, and the Svelte page's
  effect copied the first selected key's settings to the other selected keys on
  mount, so keys selected on Remap or Lighting were overwritten just by opening
  Performance (unnoticed in Svelte, whose keycaps showed no values). The brush
  rules: the first key selected while the page is open (or already selected
  when it opens) is loaded, which writes nothing; every change writes the
  settings to all selected keys; keys added to the selection take them at once,
  also after deselect-all; switching layers never writes. Keys selected before
  the page opened keep their values until the first change.
- **Reload when the keyboard loads a configuration** (D2: the UI never edits a
  stale snapshot; D7): after a profile switch from the toolbar's dropdown, the
  keyboard's own profile keys or a reset, the page starts over as when it
  opens: the first selected key of the new configuration is loaded and nothing
  is written, and without a selection the brush is no longer loaded. Nothing
  loaded from the previous profile is written to the new one. Svelte's profile
  switch never reached the keyboard (§2).
- **Rapid trigger mode** (D12): the rapid trigger switch's mode (rapid, or
  normal analog) is written once any setting differs from what was loaded, as
  Svelte always did, so a key in digital or speed mode becomes a normal analog
  key with the first change. Until then the brush is the first selected key
  exactly, its mode included: keys added to the selection take that key's own
  mode, also digital or speed mode, while the switch shows rapid trigger off.
  Svelte wrote the switch's mode on selection too.

### Debug

- **Key Test** (inherited Svelte bug): starting to listen forgets the keys held
  so far. Releases are not seen while stopped, so a key held at Stop stayed
  "pressed" and its next press was taken for an auto-repeat and never logged.
- **Key Tracking** (bounded memory): the chart keeps the last 10 s of samples;
  Svelte kept every sample of a recording, although the axis follows the last
  500 ms. After Stop, panning and zooming out reach 10 s back.
- **Accessibility** (§7.4): the tabs are `tab`/`tabpanel`; the key picker is a
  labelled dialog (Escape, backdrop click, focus returns).

### Settings and firmware update

- **Firmware file** (§8 Update): its size (1 KiB–1 MiB) is checked before it is
  read, so a huge file is never loaded; the messages are Svelte's.
- **Update session** (D3): the update lives outside the page. Leaving the page
  neither aborts a flash nor forgets it; coming back shows its progress or
  result. Svelte destroyed the page's state: its flash ran on unseen, and the
  page started over at step 1.
- **Connecting a keyboard ends an update that has not started writing** (D3,
  D18): an update waiting for its image (after Enter Bootloader in Settings),
  for the keyboard's reboot or for the bootloader ends when a keyboard is
  connected from the connection screen: the updater starts over at step 1 and
  asks nothing of the keyboard, the shell returns to `/` again when it is
  unplugged, and app updates may apply. A running erase or download goes on.
- **Which bootloader is flashed** (§8 Update): without a click, only the one
  authorized bootloader that appeared after the app's reboot request (compared
  with a lookup taken before it). Every other device (one attached before, more
  than one new one, any device when no keyboard was connected) is flashed only
  after the user picks it in the browser's chooser, so without a reboot request
  Connect USB Device always opens the chooser. The silent lookup starts once the
  keyboard has left. Two quick clicks start one flash.
- **Accessibility** (§7.4): the update steps are a list with
  `aria-current="step"`, the flash progress a `progressbar`, the error panel an
  `alert`; the Settings confirmations are labelled dialogs with focus return.
